# Linear Style Design

这是一套 Linear 风格的跨架构设计规范，来自对官方文章、公开页面实测、桌面客户端逆向和 WCAG 对比度算术的交叉核验（详见 `references/principles-and-evidence.md`）。不是从截图直接扒色板——每条规则背后都有证据边界，遇到和截图不符的地方，边界说明会解释为什么。

## 先判断意图，再决定怎么用

**意图 A：生成/实现新界面或组件**（用户要做一个 Linear 风格的 UI、页面、组件库、主题）

1. 读本文件下方的"核心设计 DNA"和"最常用默认值速查"，建立整体判断框架。
2. 复制 `assets/linear-tokens.css` 作为项目的 token 起点，按项目实际品牌色/字体调整（替换品牌色时注意重新检查各状态对比度，见 `references/color.md`）。
3. 按需读取对应主题的 reference 文件（见下方的目录），只读当前任务涉及的部分——不需要一次性读完全部八个文件。
4. 实现时遵循 `references/implementation.md` 的三层结构和最小实施顺序，不因为"要像 Linear"引入不必要的构建链或依赖。
5. 完成后用 `references/review-checklist.md` 的 Definition of Done 自查。

**意图 B：审查/诊断现有界面是否符合 Linear 风格**

1. 直接读 `references/review-checklist.md`：反模式表、五个审查问题、输出结构。
2. 发现具体问题时，交叉查对应主题文件（颜色问题查 `color.md`，字体问题查 `typography.md`，组件状态问题查 `components.md`，动效/可访问性问题查 `motion-a11y.md`）核实规则依据，不要凭印象断言。
3. 按 `review-checklist.md` 末尾的"输出结构"汇报，区分"真问题"和"规范允许的场景变化"——不是所有和 Linear 截图不一样的地方都是缺陷，参见下方"三类场景"。

两种意图可能在同一个任务里交替出现（例如先诊断，再修复），按需来回查阅即可。

## 核心设计 DNA（两种意图都要遵守）

**一句话定义：** Linear Style 是以任务为中心，通过近中性的表面、清晰而克制的排版、稳定的信息密度、精确对齐和快速可预期的交互，降低持续工作中的认知负担。它不是"黑底 + 紫光 + Inter"，也不是把整个页面的对比度压低。

| 维度 | 统一要求 |
|---|---|
| 注意力 | 内容先于应用外壳；导航和工具栏不持续争抢注意力 |
| 色彩 | 近中性色作为主体；一个品牌强调色族；语义色和数据色独立 |
| 层级 | 优先用对齐、间距、字号、适度字重和明度建立关系 |
| 结构 | 先考虑分组与留白，再考虑分隔线；不把所有信息切成卡片 |
| 密度 | 按输入方式和任务选密度；桌面紧凑不等于手机缩小 |
| 形状 | 小到中等圆角，普通表面无外投影；浮层才使用浮层阴影 |
| 反馈 | 本地响应迅速、状态明确、布局稳定、失败可恢复 |
| 操作 | 键盘和指针都能完成任务；快捷键是加速器，不是唯一入口 |
| 可访问性 | 必要信息清楚可读；焦点、状态和控件边界不为"安静"而消失 |
| 一致性 | 组件使用语义 token；主题变化不要求重写组件 |

深入理解这些原则背后的判断方法（"为什么结构应该被感受到而不是被画满"之类），读 `references/principles-and-evidence.md`。

## 三类场景，不能混为一谈

同一套原则会按场景落地成不同的具体数值，不能把工作型产品截图的紧凑感直接套到营销页或阅读场景：

| 场景 | 首要目的 | 应继承 | 不应机械照搬 |
|---|---|---|---|
| 工作型产品 UI | 持续、高频、准确完成任务 | 紧凑布局、弱化外壳、稳定列表、键盘效率 | 营销大字、环境光、长入场动画 |
| 营销 / 品牌页面 | 解释价值、展示产品、引导行动 | 排版纪律、真实产品画面、克制色彩 | 28px 行和 13px 密集正文 |
| 文档 / 设置 / 移动阅读 | 理解信息、准确输入 | 清晰结构、语义颜色、可读正文 | 为"像 Linear"压缩文字和触控目标 |

开始任何实现或审查之前，先确认当前任务属于哪一类场景——这决定了接下来该用哪组默认值。

## 最常用默认值速查

不需要每次都展开 reference 文件查这些最高频的数值，直接用：

| 项目 | 默认值 | 场景变化 |
|---|---|---|
| 深色画布 / 表面 / 浮层 | `#09090a` / `#121213` / `#1b1b1c` | 可整体换冷灰，不要零散混用两套中性灰 |
| 浅色画布 / 表面 / 浮层 | `#f9f9fa` / `#ffffff` / `#ffffff` | 浅色不是深色逐值反相 |
| 品牌强调色 | `#5e6ad2` | 可替换；换色后必须重查各状态对比度 |
| 主要操作按钮 | 工作型 UI 默认反色；登录/品牌流程可用强调色 | 同一操作层级内保持统一 |
| 字体 | Inter Variable（拉丁）+ 本地文字回退；代码/ID 用等宽栈 | 中日韩需要实测字面和行高 |
| 字重 | 400 / 500 / 600（阅读/UI/强调） | 官网拟合可用 400/510/590，需确实加载可变字体 |
| UI 文字 | 桌面 13px，中文 14px；正文 15px | 阅读区 16px |
| 间距刻度 | 4px 主刻度（2/4/8/12/16/20/24/32/40/48/64...） | 2px 允许用于微间隙 |
| 控件高度 | 默认 32px，紧凑 28px，触控 ≥44px | 一个列表内不要混用 |
| 侧栏 / 应用头部 | 240px / 最小 44px | 可因内容、语言调整 |
| 圆角 | 按钮/输入 8px，菜单项 6px，面板/对话框 12px，pill 仅用于营销 CTA/登录/紧凑控件 | 不要全局统一成一个值 |
| 动效 | hover 100ms，菜单 160ms，对话框 200ms；缓动 `cubic-bezier(.25,.46,.45,.94)` | 高频操作可 0ms |
| 文字对比度 | 正常文字 ≥4.5:1，必要图形/控件边界 ≥3:1 | 合成后的最终颜色检查，不只看字面 rgba |

完整 token 表（含 CSS 变量名）在 `assets/linear-tokens.css`，可直接复制进项目。

## Reference 文件目录

按需读取，不必每次全读：

| 文件 | 内容 | 什么时候读 |
|---|---|---|
| `references/principles-and-evidence.md` | 设计哲学判断方法、三类场景详解、证据标签说明、已知歧义点 | 需要理解"为什么"、或要向用户解释某条规则的依据时 |
| `references/color.md` | 完整语义色 token、表面规则、主要操作/强调色、系统反馈色、主题策略 | 做颜色、主题、深浅色切换相关工作时 |
| `references/typography.md` | 字体角色、字重决策、完整字阶表、字距、行长 | 做排版、字号、中英文混排相关工作时 |
| `references/layout.md` | 间距刻度、密度分档、应用外壳布局、营销布局、响应式断点、圆角/边框/阴影/材质 | 做页面结构、布局、响应式、圆角阴影相关工作时 |
| `references/components.md` | 组件状态契约、按钮/输入/导航/列表/卡片/菜单/对话框/小组件的完整规格 | 实现或审查具体组件时 |
| `references/motion-a11y.md` | 动效时间表、加载反馈、乐观更新边界、键盘快捷键、对比度与焦点、尺寸缩放、W3C 来源 | 做动效、loading、键盘交互或可访问性审查时 |
| `references/implementation.md` | 三层 token 架构、各类前端框架映射、唯一可信来源原则、最小实施顺序、CSS 参考使用约定 | 搭建项目 token 体系或决定技术落地方式时 |
| `references/review-checklist.md` | 反模式表、五个审查问题、Definition of Done、审查报告输出结构 | 做审查/诊断工作流（意图 B）时的主要入口 |

## 重要边界

- 本规范不是 Linear 官方设计系统，不提供其 Logo、wordmark 或专有图形的复刻方式；也不应被包装成"Linear 官方标准"对外宣称。
- 所有具体数值（token 表、组件尺寸、断点、CSS 示例）除标注"官方"/"实测"外，均为规范层面的统一选定值，不是对 Linear 全产品"必然如此"的断言——遇到与某个截图不符的情况，先判断是否属于规范允许的场景变化。
- 完整合规仍需结合真实产品的可访问性审计、用户测试和品牌设计评审，本规范只是可执行的实施基线。
