# 颜色、主题与语义 token

## 四种职责，不得混用

| 系统 | 作用 | 示例 token | 不得混用 |
|---|---|---|---|
| 中性基础 | 画布、表面、文字、边界 | `bg.canvas`、`text.muted` | 不拿品牌紫代替所有结构灰 |
| 品牌与交互 | 品牌动作、链接、焦点 | `accent.fill`、`text.link`、`focus.ring` | 不把某个按钮填充直接当文字链接颜色 |
| 系统反馈 | 成功、警告、错误、信息 | `feedback.danger.fg` | 不等于项目工作流里的 Done / In Progress |
| 业务与数据 | 状态、优先级、分类、图表 | `workflow.review`、`chart.series.1` | 不覆盖系统错误、焦点和品牌动作 |

**命名原则：按用途命名，不按外观命名。** `text.muted` 优于 `gray.500`，`action.primary.bg` 优于含混的 `primary`。

## 表面规则

1. 深色下，浮层通常比背景略亮；不要求每个嵌套容器都升一层亮度。
2. 浅色下，浮层可以与白色工作面相同，依靠边界、遮罩和阴影说明浮起关系；不是"越高越灰"。
3. 侧栏与画布同色或低存在感，不要求"侧栏一定比 canvas 更黑"。
4. `bg.subtle` 是区域用途，不是物理海拔。避免把所有 token 排成一条强制阶梯。
5. 半透明状态色必须与底层表面合成后检查；不要只看 rgba 字面值。
6. `state.hover` 是覆盖色，不要直接覆盖不透明背景，导致透明区域穿透。可用背景图层或先合成颜色。
7. 深浅主题各自校准文字和状态，不只换背景。
8. `text.muted` 的基础表面对比度通过，不代表叠加选中/按下底后仍通过。本规范在 pressed/selected 的中性底上将可读文字至少提升为 `text.secondary`，同时保留焦点和选中标记。
9. `state.selected` 的不透明度必须与 `state.pressed`、`state.hover` 区分，不能三者取同一个值；否则选中态会被按下或悬停态的视觉效果吞掉，与状态优先级要求矛盾（见 `components.md` 的状态契约）。

## 主要操作与强调色

| 角色 | 深色默认 | 浅色默认 |
|---|---|---|
| `action.primary.bg` | `#e5e5e6` | `#1b1b1b` |
| `action.primary.fg` | `#09090a` | `#ffffff` |
| `action.primary.hover` | `#ffffff` | `#303033` |
| `accent.fill` | `#5e6ad2` | `#5e6ad2` |
| `accent.fillHover` | `#5661c4` | `#5661c4` |
| `accent.fillPressed` | `#4f5bc4` | `#4f5bc4` |
| `accent.onFill` | `#ffffff` | `#ffffff` |

- 工作型产品默认用反色主要操作，减少大块品牌色。
- 登录、首次引导、关键品牌转化流程可使用强调色主要操作；应在该流程中统一。
- 强调色按钮的 hover 不强制"深色变亮"；先保证白字对比度，本规范选定略深的 hover。
- 一个操作组默认一个主动作；桌面页面里打开模态时，背景页面的主按钮不算另一个竞争动作，因为背景不可交互。
- 焦点、链接和选中状态可以同时出现；不得为了"一个彩色载体"隐藏其中任何一个。
- 不设置 2%/5% 的像素预算硬门槛；用视觉重心和任务优先级验收。

## 系统反馈与业务状态

| 系统语义 | 深色前景 | 浅色前景 | 用途 |
|---|---|---|---|
| success | `#27a644` | `#198038` | 保存完成、验证通过 |
| warning | `#f2c94c` | `#8a6500` | 风险、需要注意 |
| danger | `#eb5757` | `#c03434` | 错误、危险操作 |
| info | `#8fa6ff` | `#4f5bc4` | 中性信息提示 |

- 反馈文字可以直接使用对应前景，但必须针对其真实背景复检；不要默认所有 12% 同色底都达标。
- Badge 默认中性文字 + 状态点/图标，需要更强反馈时才加低透明度底。
- 工作流状态必须按业务命名与映射：`workflow.todo / active / review / done / canceled`。
- 不规定 Done 一定绿色或靛蓝，不规定 In Progress 一定绿色或黄色——业务状态色与系统反馈色是两套独立映射。
- 颜色之外保留文案、形状、图标或其他可识别线索。
- 图表色可以多于一种；使用稳定映射、图例、标签，必要时使用线型与纹理，不把所有系列染成品牌色。

## 可访问的细线，不等于所有边框都很淡

弱容器线可低于 3:1，因为它们不是识别控件的唯一视觉依据。**但文本输入边界、未选复选框、开关轨道、重要状态指示不能一律复用白色 6% 边框。**

- 输入框默认使用 `border.control`，或提供其他满足识别要求的边界/背景。
- 已有清楚文字或图标的按钮可用弱边框，不能因此推导所有表单控件都能用弱边框。
- 焦点环必须是足够清晰的实质指示；25% 透明的模糊光晕只能做补充。
- 高对比模式可加重边界；"更明显"不违反 Linear Style。

## 主题策略与生成器

Linear 官方基于 LCH，从 base、accent、contrast 三种输入生成主题，避免每个主题手设 98 个变量。[O]

**实施默认：**

1. 先使用静态深浅语义 token；不为复刻 Linear 建立 98 色生成器。
2. 若产品只需要一种主题，可以只实现该主题；一旦宣称支持双主题，必须校验全部状态。
3. 主题选择优先级：用户明确选择 > 跟随系统 > 产品回退。系统主题变化不覆盖用户手选。
4. 主题同时覆盖浮层、原生表单配色、滚动区及嵌入区域；避免只改内容卡片。
5. 多品牌替换必须覆盖品牌填充、其前景、链接、焦点、弱填充和 hover，而不是只改一个 hex。

**确需动态主题时：**

- 使用感知色彩空间可以改善派生一致性，但不能替代对比度测试。
- CIELCH 与 OKLCH 的数值尺度不同，不能把 `[12,2,270]` 或 `[55,80,300]` 原样塞进 `oklch()`。
- 出色域颜色需要映射；必须用最终实际输出的颜色检查对比度。
- `contrast` 输入不天然等于 WCAG 合规；高对比模式也需要验证。
- 逆向所得参数只可作为研究线索，不作为"官方生成公式"。

## 统一默认色板速查

| 项目 | 默认值 | 允许的场景变化 |
|---|---|---|
| 深色画布 / 表面 / 浮层 | `#09090a` / `#121213` / `#1b1b1c` | 可以整体换成冷灰，但不能零散混用两套中性灰 |
| 浅色画布 / 表面 / 浮层 | `#f9f9fa` / `#ffffff` / `#ffffff` | 浅色不是深色逐值反相 |
| 品牌强调 | `#5e6ad2` | 可整体替换；必须重新检查各状态对比度 |
| 主要操作 | 默认反色按钮 | 登录、转化、品牌流程可统一采用强调色按钮 |
